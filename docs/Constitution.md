# Constitution

The design philosophy and rules for Project Altitude. Read this first.

---

## What this product is

A calm, recommendation-driven flight booking app. The interface helps users decide instead of forcing them to compare. Every design decision should answer one question: **does this make booking easier?**

---

## Principles

**Simplicity first.** Every screen has one primary purpose. If two actions compete for attention, one needs to go.

**Progressive disclosure.** Only show information when it becomes relevant. Users should never feel like they're filling out a form.

**Recommendation over comparison.** Present curated options with clear reasons. Allow alternatives without encouraging endless browsing.

**Familiar before innovative.** Improve calendars, search, and lists rather than replacing them. Innovation should reduce friction, not create it.

**Thumb-first interaction.** Primary actions belong in the bottom third of the screen. Search, CTAs, and selection controls should be reachable with one hand.

**Consistency.** The same interaction behaves the same way everywhere. Users never wonder "will this screen work differently?"

---

## Visual language

The interface should feel calm, spacious, minimal, confident, and premium.

Avoid visual noise, heavy borders, bright gradients, excessive colors, and decoration. Neutrals compose roughly 90% of the interface. Color communicates meaning, never decoration.

---

## UX rules

Every screen should have one primary action, clear visual hierarchy, predictable navigation, and minimal cognitive load.

Always prefer recognition over recall, selection over configuration, guidance over exploration, simplicity over flexibility.

---

## Content voice

Clear, calm, helpful, human, confident. Never promotional, robotic, technical, or overly casual. See CONTENT_GUIDELINES.md for terminology and formatting rules.

---

## Design checklist

Before shipping any screen, ask:

- Does this screen have one primary purpose?
- Is the next action obvious?
- Can anything be removed?
- Does it reduce cognitive load?
- Does it support one-handed use?
- Is the interface visually calm?
- Is the language clear and in sentence case?
- Does it follow existing patterns?
- Would a first-time traveller understand it without explanation?
- Do touch targets meet 48×48 minimum?
- Does it respect reduced motion preferences?

If any answer is no, revise the design.

---

## MVP scope

This design system currently supports only the flight booking flow: Home, Airport Search, Date Selection, Passenger Selection, Flight Recommendations, Booking. Future travel features extend this system without changing its principles.
